# pm-prd-writer

把已经确认“为什么做、为谁做、做什么”的产品需求框架写成可执行的 PRD。你负责规格化和补漏，不负责替用户选择产品方向。

## 输入契约

合法输入至少包含一份现成的产品需求框架，或等价材料。用户提供框架并要求产出 PRD 时，将该框架视为写作基线，不重复执行需求发散或要求用户再次确认整份框架。开始写作前只检查：

- 问题定义
- 目标用户
- 核心场景
- 产品目标或成功标准
- 已选方案方向
- 产品方案大纲
- 功能模块及各模块核心能力
- 本期范围和非范围
- 核心流程
- 已知约束与依赖

材料不必使用固定模板，但这些核心决策必须能从材料中找到。框架明确标为草稿、存在互相冲突的方向，或缺少阻塞项时才判定为未就绪。已有 PRD 的补全和修订不要求另做需求框架，但不得改变其产品方向，除非用户明确要求。

## 就绪检查

先区分三种情况。

### 已就绪

核心决策均已确认。直接生成 PRD。

### 有条件就绪

核心方向已确认，只缺少不会改变方向的实现细节。可以生成 PRD，但把缺口标为 `[待确认]`，说明建议值和影响范围。

### 未就绪

以下任一项不明确时，不生成 PRD：

- 不知道解决什么问题
- 目标用户或核心场景不明确
- 多个产品方向尚未选择
- 本期范围没有边界
- 核心流程仍在发散

此时只输出：

```markdown
## PRD 就绪检查
- 状态：未就绪
- 已具备：...
- 阻塞项：...
- 下一步：使用 pm-requirement-framer 完成并确认产品需求框架
```

不要在本 Skill 中自行补做需求框架，也不要通过大量 `[假设]` 绕过输入门槛。

## 写作依据

建立一张内部映射，确保 PRD 每项核心设计都能追溯到需求框架：

| PRD 内容 | 需求框架依据 |
|---|---|
| 背景与目标 | 问题、依据、产品目标 |
| 目标用户与权限 | 目标用户、核心场景 |
| 功能范围 | 本期范围、非范围 |
| 功能清单 | 产品方案大纲、功能模块与核心能力 |
| 主流程 | 已确认方案、核心用户路径 |
| 验收标准 | 成功指标、已确认决策 |

需求框架没有支持的内容不能写成确定事实。发现方向冲突时停止并请用户确认，不要让 PRD 偏离原始需求。

## 工作流

### 1. 读取模板

读取 [`references/prd-template.md`](references/prd-template.md)。按需求规模裁剪章节，不为简单功能制造无意义的数据库或系统架构内容。

### 2. 生成 PRD 主体

PRD 包含以下结构：

1. 概述：背景、产品目标、目标用户、名词和角色权限
2. 产品描述：范围、整体流程、全局规则、版本和功能清单
3. 功能需求：用户故事、前后置条件、交互、流程、异常和数据字典
4. 非功能需求：安全、统计、性能、数据和系统集成
5. 附录：验收标准与测试要点

写作要求：

- 描述要能被开发和测试执行，删除“提升体验”“优化性能”等空话。
- 用户故事使用“作为 [角色]，我希望 [操作]，以便 [目的]”。
- 流程适合图示时使用 Mermaid，同时保留文字说明。
- 字段定义使用表格，包含类型、必填、规则和示例。
- 不把模板中的示例值当成真实需求。无依据参数标为 `[待确认]`。

### 3. 自动补漏

把发现的问题写回对应章节，不单独堆放一个“补漏”章节。检查：

- 输入校验、空状态、重复提交、权限不足和失败反馈
- 关键状态及其合法转换
- 核心操作、成功和异常事件的埋点
- 敏感数据、权限、审计、存储周期和合规要求
- 外部系统依赖、同步方式、超时和降级
- 可执行的验收条件

无法从框架或材料判断的实现细节使用 `[待确认]`。每项附建议值及不确认的影响。不得用补漏过程扩张本期范围。

### 4. 做方向一致性检查

交付前逐项核对：

- PRD 解决的问题与框架一致
- 目标用户和场景没有扩大
- 功能清单没有超出本期范围
- 功能模块和能力没有偏离方案大纲
- 核心流程实现的是已选方案
- 成功指标可以验证产品目标
- 新增假设均为实现细节，不是产品方向

发现不一致时优先修改 PRD。若需求框架本身相互矛盾，列出冲突并等待用户决策。

## 交付物

### 1. 评审版 PRD

默认输出 Markdown，文件名为 `[产品名]_PRD_V[版本号].md`。用户要求 `.docx` 时，使用当前环境可用的文档 Skill 创建并检查文档。

保留所有 `[待确认]` 标记，并在文档头部注明需求框架名称或来源，方便追溯。

### 2. 待确认项清单

从 PRD 汇总所有 `[待确认]`：

- 按“阻塞开发、影响完整度、可后续补充”排序
- 每项给出默认建议和影响范围
- 如果出现产品方向级待确认项，就绪检查有误，应停止交付并返回 `pm-requirement-framer`

### 3. 交接摘要

用不超过十行说明本次 PRD 的范围、核心流程、重要决策、剩余阻塞项和建议下游。

## 质量检查

- 背景、目标和成功指标可追溯到需求框架
- 角色权限和范围边界明确
- 主流程闭环，关键状态完整
- 功能描述包含正常流程和异常流程
- 数据字段、校验和操作反馈明确
- 安全、数据、性能和集成要求有依据或标为待确认
- 核心功能有可执行验收标准
- 没有未经确认的范围扩张
- 没有把产品方向写成假设后继续交付
- 文档版本、来源和待确认项完整

## 上下游衔接

- 上游：`pm-requirement-framer` 输出并经用户确认的需求框架，或等价的已确认产品材料。
- 下游：`pm-review-board`、`pm-tracking-spec-writer`、`pm-experiment-designer`。
- 评审问题可以返回本 Skill 修订。涉及目标用户、方案方向或范围变化时，应先回到 `pm-requirement-framer` 更新并重新确认框架。
