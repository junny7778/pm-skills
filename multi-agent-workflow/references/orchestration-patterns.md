# 工作流编排模式

只选择当前任务真正需要的模式。不同模式可以组合使用。

## 顺序移交

当后续工作依赖前一个阶段的产物时使用。

示例：

```text
研究 -> 方案 -> 实现 -> 验证
```

阶段之间传递正式产物，不要传递无关的完整对话历史。

## 并行分工

当多个方向可以独立处理时使用。

示例：

```text
代码调查
├── 调用关系追踪
├── 数据模型检查
└── 问题复现
```

所有必要分支完成后，由主 Agent 对结果进行比较和整合。

如果多个 Agent 会修改相同文件，或者依赖持续变化的共享状态，则不能并行执行。

## 产出和审查

当一个 Agent 负责产出，另一个 Agent 负责独立判断时使用。

示例：

```text
产出 Agent -> 审查 Agent
                ├── PASS -> 继续
                ├── REJECT -> 修改 -> 重新审查
                └── BLOCKED -> 主 Agent 处理或询问用户
```

审查 Agent 不得直接修改它正在审查的产物。

## 竞争方案

当任务存在重要设计选择，而且没有明显最佳方案时使用。

让两个或多个 Agent 提出结构上确实不同的方案。将原始要求和候选方案提供给独立评估 Agent。最终选择由主 Agent 负责。

不要将此模式用于普通的实现细节。

## 分片和汇总

当大型输入可以拆分成相互独立的部分时使用。

示例：

```text
数据集或代码仓库
├── A 部分分析
├── B 部分分析
└── C 部分分析
        ↓
统一汇总和交叉检查
```

必须明确分片边界，避免重复处理或遗漏。

## 调查、执行和验证

适用于故障诊断和实现任务。

```text
调查 Agent -> 执行 Agent -> 验证 Agent
```

调查 Agent 负责识别原因和约束。执行 Agent 负责修改其拥有的产物。验证 Agent 负责检查真实行为和回归风险。

## 动态调整

如果新证据表明原工作流不再适用，主 Agent 可以调整工作流，包括修改任务依赖、增加必要的专业 Agent、删除不再需要的工作或停止没有价值的分支。

调整工作流不得在未说明的情况下扩大用户目标或权限。
