# 多 Agent 工作流

协调多个子 Agent 完成用户目标。根据当前任务动态设计工作流，不使用固定角色或固定阶段。

## 基本要求

使用本 Skill 时：

1. 保留用户的目标、约束、权限和交付要求。
2. 确认当前环境提供子 Agent 协作工具。
3. 根据实际工作建立一个尽可能小的执行图。
4. 将有明确边界、可以独立完成的职责委派给子 Agent。
5. 由一个主 Agent 负责协调、状态管理、结果整合和最终回复。
6. 在宣布完成前检查真实产物。

不得通过在一段回复中扮演多个角色来模拟子 Agent。

如果当前环境没有子 Agent 协作工具，应明确说明。只有当用户接受单 Agent 降级方案，或者任务仍可在不虚构多 Agent 执行过程的情况下完成时，才继续执行。

## 规划工作流

开始委派前，确定：

- 预期结果；
- 完成条件和验收标准；
- 可用输入和相关项目状态；
- 任务需要的专业能力；
- 各项工作之间的依赖关系；
- 哪些工作可以安全并行；
- 哪些产物需要独立审查；
- 共享文件或状态的所有权；
- 失败处理、重试次数和停止条件。

使用能够产生实际收益的最小工作流。不要仅为了增加 Agent 数量而创建角色。

当用户明确调用本 Skill 来测试多 Agent 功能时，至少使用两个职责确实不同的子 Agent，除非当前环境不支持。

在启动子 Agent 前或启动过程中，向用户提供简短的工作流说明，包括主要职责、任务依赖关系和可能需要用户参与的审批点。

需要选择具体编排结构时，读取 [references/orchestration-patterns.md](references/orchestration-patterns.md)。

## 定义子 Agent

为每个子 Agent 提供一个有明确边界的任务合同，其中包含：

- 角色或职责；
- 目标；
- 输入和权威信息来源；
- 预期输出；
- 允许执行的操作；
- 必要时说明禁止执行的操作；
- 文件或状态所有权；
- 完成标准；
- 必须返回的证据。

创建子 Agent 任务时，读取 [references/agent-contract.md](references/agent-contract.md)。

只有角色名称不构成有效的任务合同。不要给子 Agent 分配“帮忙处理”“审查所有内容”或“把它改得更好”之类没有明确边界的任务。

只向子 Agent 提供完成任务所需的上下文。如果子 Agent 的职责是进行独立分析或审查，不要向它提供其他 Agent 的结论。只提供原始要求、正式产物和必要证据。

## 协调执行

存在依赖关系的任务必须按照依赖顺序执行。只有在职责边界清楚，并且不会修改冲突的共享状态时，才并行执行任务。

主 Agent 负责：

- 制定工作流；
- 跟踪依赖关系；
- 分派任务并等待结果；
- 在阶段之间传递已经批准的产物；
- 处理相互冲突的建议；
- 整合结果；
- 执行最终验证；
- 与用户沟通。

第一版工作流中，子 Agent 不应继续创建新的子 Agent。所有任务调度统一由主 Agent 负责。

不要允许多个并行 Agent 修改相同文件或共享状态。为每个 Agent 分配互不重叠的文件范围，必要时使用独立 Git worktree，或者将写操作改为顺序执行。

子 Agent 的报告只是待验证的结论。不能仅因为子 Agent 表示任务成功，就认定任务已经完成。

## 审查和纠正

以下情况应使用独立审查 Agent：

- 用户明确要求验证或审查；
- 某个产物决定后续工作能否继续；
- 复杂实现需要独立的正确性证据；
- 错误的代价较高或难以撤销；
- 独立意见能够明显改善结果。

产出者和审查者必须是不同的 Agent。审查者只接收原始需求、正式产物和与验收相关的证据。不要把产出者的内部推理当成完成证明。

正式关卡使用 `PASS`、`REJECT` 或 `BLOCKED`。当关卡决定后续工作能否继续时，读取 [references/review-gates.md](references/review-gates.md)。

如果结果为 `REJECT`，将问题交给具备修改能力的 Agent 处理。修改完成后，必须重新执行相关审查。除非用户指定其他次数，默认最多执行两轮纠正。

## 产物和状态

用户需要长期保留的交付物，应写入符合当前项目习惯的文件位置。

对于规模较大的工作流，维护一份简洁的工作流记录，包含目标、工作流阶段、当前状态、各阶段负责人、已完成的产物、关卡决策和尚未解决的阻塞问题。

如果任务规模较小，并且能够通过当前对话可靠跟踪进度，则不需要额外创建工作流文档。

临时协调材料不应混入用户正式交付物。不得为了强行套用工作流结构而覆盖项目中已有的文件。

## 权限和范围

任务委派不会扩大用户授予的权限。每个子 Agent 都继承当前任务的范围和适用的权限边界。

如果用户没有明确要求，不得通过本工作流执行部署、发布、对外发送消息、购买、破坏性操作或与当前目标无关的修改。

如果必要操作需要新的授权，或者需要用户做出会实质影响结果的选择，应先完成范围内所有安全的准备工作，然后在对应关卡暂停并询问用户。

## 完成条件

结束工作流前：

1. 检查真实交付物。
2. 执行适合当前任务的检查。
3. 将结果与原始验收标准逐项对照。
4. 解决差异，或者明确报告尚未解决的问题。
5. 汇总工作流，但不要暴露隐藏的内部推理过程。

最终回复应说明最终结果、委派的职责、创建或修改的内容、执行过的验证、尚未解决的限制，以及是否需要用户进一步操作。

除非用户明确要求，不要输出完整的 Agent 内部对话。
