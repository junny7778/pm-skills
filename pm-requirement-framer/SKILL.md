# pm-requirement-framer

先把需求方向定清楚，再进入 PRD。交付物是可讨论、可选择、可确认的需求框架，不是功能规格书。

## 边界

- 必须输出产品级方案大纲，包括功能模块、模块能力、核心用户路径和模块边界。
- 不输出详细字段、页面级交互、异常规则、接口或数据库设计。这些属于 PRD。
- 不把推测写成事实。用 `[事实]`、`[用户确认]`、`[假设]`、`[待验证]` 标记信息性质。
- 不替用户静默选择产品方向。提出选择，说明差异，给出推荐依据。
- 目标用户、核心问题、方案方向或本期范围未确认时，状态不能是“已就绪”。
- 用户已经提供产品需求框架并要求产出 PRD 时，直接转 `pm-prd-writer`，不要要求重复梳理或再次确认整份框架。

## 工作流

### 1. 保存需求原点

先用接近原话的一到三句话记录用户最初的需求。后续方向必须能追溯到这段原始表述。

### 2. 识别已知信息和关键缺口

提取问题、用户、场景、目标、现有解决方式、约束和证据。优先询问会改变产品方向的问题，一轮不超过五个。文案、分页数量等实现细节不在此阶段追问。

用户暂时无法回答时，保留为未知项并说明验证方式。不要编造用户研究、业务数据或技术约束。

### 3. 判断是否存在多个方案方向

有真实选择空间时给出两到三个方案。每个方案说明核心做法、解决机制、覆盖范围、收益、成本、风险、依赖和待验证假设。

如果只有一个合理方向，不为凑数量制造伪选项。仍需说明为什么其他明显方向不适用。

用户已经明确指定方向时，不再生成备选方案，只检查该方向是否与问题、目标和约束一致。

### 4. 确定方案方向

给出推荐方向和依据，但将最终选择留给用户。用户确认前可以迭代需求框架，不能进入详细 PRD。

只有一个合理方向或用户已经指定方向时，直接将其作为当前方向，并注明成立条件。

### 5. 展开产品方案大纲

围绕当前方向输出整个产品方案的骨架。至少包含：

- 产品如何解决目标问题
- 用户从进入到获得结果的核心路径
- 功能模块划分
- 每个模块提供的核心能力
- 模块之间的关系或依赖
- 本期模块与后续模块的边界

功能模块写到“能力”层级，例如“知识库管理提供内容导入、分类和检索能力”。不要提前写输入框长度、按钮位置、接口字段或报错文案。

如果方向尚未由用户确认，仍可展开推荐方向的大纲，但必须标记为 `[待确认方案]`，就绪状态保持“未就绪”。

### 6. 判断 PRD 就绪状态

- `未就绪`：问题、用户、方向或范围仍不明确。
- `有条件就绪`：核心方向已确认，但有少量不阻塞结构设计的未知项。
- `已就绪`：核心信息均已确认，可以交给 `pm-prd-writer`。

只有“有条件就绪”或“已就绪”才能输出 PRD 交接摘要。“有条件就绪”必须列出剩余事项及其影响。

## PRD 交接摘要

需求达到就绪条件后，在框架末尾附加：

```markdown
## PRD 交接摘要
- 需求名称：
- 原始需求：
- 问题定义：
- 目标用户：
- 核心场景：
- 产品目标：
- 成功指标：
- 已确认方案：
- 方案概述：
- 功能模块：
- 各模块核心能力：
- 本期范围：
- 非范围：
- 核心流程：
- 约束与依赖：
- 已确认决策：
- 非阻塞待确认项：
- 就绪状态：有条件就绪 / 已就绪
```

不要在摘要里加入框架正文中没有依据的新结论。

## 上下游衔接

- 上游可以是原始想法、会议纪要、用户反馈、数据洞察、竞品结论或 `pm-advisory-board` 的判断。
- 下游是 `pm-prd-writer`。只有用户确认过的需求框架才能进入下游。
